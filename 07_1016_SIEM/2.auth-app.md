# 인증 앱과 대응 앱으로 경보 수신·계정 차단·복구 확인하기

인증 앱 `auth_app.py`는 테스트 계정의 로그인과 차단·복구를 담당합니다. 대응 앱 `soar_app.py`는 SIEM 경보를 수신·검증하고, `high`·`critical` 경보를 받으면 인증 앱의 차단 API를 호출합니다. 두 앱을 실행한 뒤 [Kibana SIEM 설정](1.kibana-siem.md)에서 경보 전송을 연결합니다.

```text
SIEM 경보 → 대응 앱 → 인증 앱 /block
                           ↓
                      /login 요청 실패
```

## 1. 앱 실행

`2609_kookmin_rag` 저장소 루트에서 터미널 두 개를 엽니다. `07_1016_SIEM` 폴더가 바로 보이는 위치이며, Windows·Mac에서 같은 명령을 사용합니다.

터미널 1 — 인증 앱:

```sh
uv run --script "./07_1016_SIEM/auth_app.py"
```

터미널 2 — 대응 앱에 인증 앱 주소 연결:

```sh
uv run --script "./07_1016_SIEM/soar_app.py" --login-url http://127.0.0.1:8082
```

대응 앱이 실행 중이면 종료한 뒤 위 명령으로 다시 실행합니다.

스크립트 상단에 필요한 패키지가 선언되어 있어 `uv`가 FastAPI·Pydantic·Uvicorn·HTTPX 실행 환경을 준비합니다. 최초 실행에는 인터넷 연결이 필요합니다.

다음과 같이 표시되면 대응 앱이 준비된 것입니다. 두 앱을 실행한 터미널을 유지합니다.

```text
Uvicorn running on http://127.0.0.1:8081
```

브라우저에서 `http://127.0.0.1:8081/health`를 열어 다음 응답을 확인합니다.

```json
{"status": "ok"}
```

Kibana와 두 앱은 같은 컴퓨터의 루프백 주소로 연결합니다. Kibana를 Docker나 다른 서버에서 실행하면 그 환경에서 대응 앱에 접근 가능한 주소와 바인딩을 설정합니다.

### 1.1 대응 앱의 입력과 출력

| 메서드·경로 | 역할 |
|---|---|
| `GET /health` | 앱 실행 확인 |
| `POST /webhook/siem` | 경보 JSON 검증·출력, 인증 앱에 차단 요청, 수신 결과 응답 |
| `GET /docs` | 요청 모델 확인과 직접 호출 |

`SiemAlert`는 `alert_id`, `rule_id`, `rule_name`, `severity`, `action_time`을 필수 필드로 받습니다. ID·이름·시각은 빈 문자열을 허용하지 않고, `severity`는 `low`, `medium`, `high`, `critical` 중 하나를 사용합니다. 모델에 맞지 않는 요청은 `422`로 응답합니다.

### 1.2 경보 수신 확인

브라우저에서 `http://127.0.0.1:8081/docs`를 열고 `POST /webhook/siem`에 다음 JSON을 보냅니다.

```json
{
  "alert_id": "connector-test-001",
  "rule_id": "manual-test",
  "rule_name": "Webhook 연결 테스트",
  "severity": "low",
  "action_time": "manual-test"
}
```

`received: true`, `alert_id: connector-test-001` 응답과 터미널의 `SIEM webhook received`를 확인합니다. `low` 경보는 수신·출력하고, `high`·`critical` 경보는 인증 앱에 차단을 요청합니다.

[FastAPI 요청 본문과 Pydantic 모델](https://fastapi.tiangolo.com/tutorial/body/)

## 2. 로그인 성공 확인

브라우저에서 `http://127.0.0.1:8082/docs`를 열고 `POST /login`에 다음 JSON을 보냅니다.

```json
{"username": "admin", "password": "1234"}
```

`200`과 `로그인 성공` 응답을 확인합니다.

## 3. 경보 전송과 차단 확인

`http://127.0.0.1:8081/docs`를 열고 `POST /webhook/siem`에 다음 JSON을 보냅니다.

```json
{
  "alert_id": "login-test-001",
  "rule_id": "manual-test",
  "rule_name": "반복 로그인 실패 탐지",
  "severity": "high",
  "action_time": "manual-test"
}
```

대응 앱이 인증 앱의 `/block`을 호출하고, 응답의 `action`에 `blocked: true`가 표시됩니다. 같은 계정으로 `/login`을 다시 호출하면 `403`과 `계정이 차단되었습니다`를 확인할 수 있습니다.

## 4. 계정 복구

인증 앱의 `/docs`에서 `POST /unblock`을 실행합니다. 다시 `/login`을 호출해 로그인 성공을 확인합니다.

계정 상태는 메모리에 저장하며, 인증 앱을 재시작하면 차단이 해제됩니다.

## 5. 실제 SIEM 경보 연결

[Kibana SIEM 자료의 4~7절](1.kibana-siem.md#4-webhook-connector-등록)에 따라 Connector·Actions를 설정합니다. Connector의 URL은 `http://127.0.0.1:8081/webhook/siem`을 사용합니다. Filebeat와 두 앱을 실행한 상태에서 [7절의 명령](1.kibana-siem.md#7-새-경보의-webhook-수신-확인)으로 현재 시각의 로그를 추가해 실제 경보를 발생시킵니다.

새 `high`·`critical` 경보가 전달되면 Spring 샘플의 로그인 실패 계정과 같은 이름인 `admin`을 차단합니다. Security Alerts의 경보 ID와 대응 앱이 수신한 `alert_id`를 비교하고, 인증 앱의 로그인 응답을 확인합니다.

| 확인 순서 | 결과 |
|---|---|
| `/login` 호출 | 로그인 성공 |
| SIEM 경보 → Webhook 수신 | 인증 앱의 `/block` 호출 |
| `/login` 재호출 | 계정 차단으로 로그인 실패 |
| `/unblock` 후 `/login` 호출 | 로그인 성공 |
