# 아이돌 밈으로 이해하는 significant_terms

`significant_terms`는 검색 결과에서 특징적인 키워드를 찾는 데 사용할 수 있지만, 그 키워드가 사용자가 원하는 검색어와 잘 맞는지는 별개의 문제다. 검색어 확장이나 추천에 적용해도 검색 품질 개선으로 바로 이어지지는 않을 수 있다.

이번에 이 집계를 다루는 이유는 **데이터 분석, 특히 SIEM에서 특정 사건이나 의심스러운 로그 집합의 특징을 찾는 데 활용할 수 있기 때문**이다. 아이돌 밈 예제로 “전체에 비해 특정 집합에서 유독 많이 등장하는 값”을 이해하고, 이를 보안 로그 분석으로 연결한다.

## 1. 먼저 예상해 보기

전체 아이돌 게시글 100개 중 코르티스 게시글은 20개다. 문서 한 개에 여러 태그가 있을 수 있다.

| 태그 | 코르티스 글 20개 중 | 전체 글 100개 중 | 코르티스 비율 / 전체 비율 |
| --- | ---: | ---: | ---: |
| 컴백 | 18개 (90%) | 90개 (90%) | 1배 |
| 직캠 | 16개 (80%) | 80개 (80%) | 1배 |
| 영크크 | 12개 (60%) | 15개 (15%) | 4배 |
| 늙크크 | 8개 (40%) | 10개 (10%) | 4배 |

- `terms`: 기본 정렬은 문서 수 내림차순이다. 코르티스 글에서 가장 많은 **컴백**이 먼저 나온다.
- `significant_terms`: 선택한 문서 집합과 배경 집합의 출현 비율을 비교한다. 이 예제에서는 **영크크**, **늙크크**가 나온다.

‘컴백’은 18개나 나오지만 전체에서도 90%의 글에 등장한다. ‘영크크’는 12개로 더 적게 나오지만 전체에서는 15%, 코르티스 글에서는 60%다. 코르티스 글에서 특히 두드러지는 태그인 셈이다.

## 2. 실습 데이터 준비

[Kibana 실행 파일](06.significant_terms_idol.kibana.txt)을 Kibana의 **Dev Tools → Console**에 붙여 넣고 요청을 위에서부터 실행한다.

1. `PUT idol_meme_demo_v1`: 인덱스와 매핑 생성.
2. `POST idol_meme_demo_v1/_bulk?refresh=wait_for`: 게시글 100개 적재. 응답의 `errors`가 `false`인지 확인.
3. `GET idol_meme_demo_v1/_count`: `count`가 100인지 확인.
4. 두 집계 비교, 배경 변경, 그룹별 집계 실행.

데이터에는 CORTIS, BTS, SEVENTEEN, aespa, TWICE 글이 각각 20개 있다. 다른 그룹 글에도 영크크 3개, 늙크크 2개를 배치해서 밈이 다른 맥락에서도 쓰이는 상황을 가정했다.

매핑의 핵심은 다음과 같다.

```json
"properties": {
  "group": { "type": "keyword" },
  "tags": { "type": "keyword" }
}
```

`tags`는 미리 부여한 태그 배열이다. 영크크와 늙크크는 각각 하나의 태그로 저장했다.

## 3. 같은 검색 결과에서 두 집계 비교

```json
GET idol_meme_demo_v1/_search
{
  "size": 0,
  "query": {
    "term": { "group": "CORTIS" }
  },
  "aggs": {
    "popular_tags": {
      "terms": {
        "field": "tags",
        "size": 10
      }
    },
    "distinctive_tags": {
      "significant_terms": {
        "field": "tags",
        "size": 10,
        "min_doc_count": 3,
        "jlh": {}
      }
    }
  }
}
```

`size: 0`은 개별 검색 문서를 생략하고 집계 결과를 확인하기 위한 설정이다.

- **Foreground**: `query`로 선택한 코르티스 게시글 20개.
- **Background**: 기본적으로 검색 대상 인덱스 전체 게시글 100개. **코르티스 글 20개도 포함한다.**

최상위 `query`가 두 집계의 수집 대상을 코르티스 글로 제한하지만, `significant_terms`의 기본 배경은 전체 인덱스다.

예상되는 `popular_tags.buckets`:

```json
[
  { "key": "컴백", "doc_count": 18 },
  { "key": "직캠", "doc_count": 16 },
  { "key": "영크크", "doc_count": 12 },
  { "key": "늙크크", "doc_count": 8 }
]
```

예상되는 `distinctive_tags`의 주요 부분:

```json
{
  "doc_count": 20,
  "bg_count": 100,
  "buckets": [
    {
      "key": "영크크",
      "doc_count": 12,
      "bg_count": 15,
      "score": 1.8
    },
    {
      "key": "늙크크",
      "doc_count": 8,
      "bg_count": 10,
      "score": 1.2
    }
  ]
}
```

`distinctive_tags.doc_count`는 선택한 전체 문서 수, 버킷의 `doc_count`는 선택한 문서 중 해당 태그가 있는 문서 수다. 바깥 `bg_count`는 배경 전체 문서 수, 버킷의 `bg_count`는 배경에서 해당 태그가 있는 문서 수다.

### background_filter: 비교 기준 바꾸기

`background_filter`는 **배경으로 사용할 문서 집합**을 지정한다. 전체 아이돌 글과 비교하는 대신, 코르티스와 BTS 글 안에서 코르티스의 특징을 찾는다면 다음처럼 설정한다.

```json
GET idol_meme_demo_v1/_search
{
  "size": 0,
  "query": {
    "term": { "group": "CORTIS" }
  },
  "aggs": {
    "distinctive_tags": {
      "significant_terms": {
        "field": "tags",
        "size": 10,
        "min_doc_count": 3,
        "jlh": {},
        "background_filter": {
          "terms": { "group": ["CORTIS", "BTS"] }
        }
      }
    }
  }
}
```

- `query`: 관심 대상인 코르티스 글 20개를 선택한다.
- `background_filter`: 비교 기준인 코르티스와 BTS 글 40개를 선택한다. 여기에도 관심 대상인 코르티스 글이 포함된다.

| 태그 | 코르티스 글에서 | 기존 배경: 전체 100개에서 | 새 배경: 두 그룹 40개에서 |
| --- | ---: | ---: | ---: |
| 영크크 | 12/20 (60%) | 15/100 (15%) | 13/40 (32.5%) |
| 늙크크 | 8/20 (40%) | 10/100 (10%) | 9/40 (22.5%) |

관심 대상의 빈도는 그대로지만 배경의 빈도와 비율이 달라져 점수도 달라진다. 응답의 바깥 `doc_count`는 20, `bg_count`는 40이고, 영크크 버킷의 `doc_count`는 12, `bg_count`는 13이다.
실데이터에서는 같은 기간·언어·커뮤니티의 글끼리 비교하도록 배경을 정할 수 있다. **“무엇과 비교해서 특징적인가?”**를 정하는 설정이다.

## 4. 그룹별 특징을 한 번에 찾기

최상위 검색 조건 없이 `terms`로 그룹별 문서를 먼저 나누고, 각 버킷 안에서 `significant_terms`를 실행할 수도 있다.

```json
GET idol_meme_demo_v1/_search
{
  "size": 0,
  "aggs": {
    "by_group": {
      "terms": {
        "field": "group",
        "size": 10
      },
      "aggs": {
        "distinctive_tags": {
          "significant_terms": {
            "field": "tags",
            "size": 10,
            "min_doc_count": 3,
            "jlh": {}
          }
        }
      }
    }
  }
}
```

각 그룹 버킷의 문서가 foreground이고 기본 배경은 전체 인덱스다. 이 데이터에서는 CORTIS 버킷에 두 표현이 나오고, 다른 그룹 버킷의 결과는 비어 있다. 다른 그룹도 공통 태그의 비율이 전체와 같고, 두 표현의 문서 수가 `min_doc_count`보다 작기 때문이다.

## 5. SIEM에서는 어떻게 활용할까?

로그인 실패가 많이 발생했을 때 “실패 로그에서 전체 로그인 로그보다 유독 많이 등장하는 계정은 무엇인가?”를 물을 수 있다. `terms`는 실패 횟수가 많은 계정을 보여주고, `significant_terms`는 배경의 계정별 출현 비율과 비교해 실패 로그에서 두드러지는 계정을 보여준다.

| 아이돌 예제 | SIEM 로그인 분석 예제 |
| --- | --- |
| 코르티스 게시글 | 조사할 로그인 실패 로그 |
| 전체 아이돌 게시글 | 같은 서비스·기간의 전체 로그인 로그 |
| `tags`의 영크크·늙크크 | `user.name`의 계정 이름 |
| 코르티스 글에서 두드러지는 태그 | 실패 로그에서 두드러지는 계정 |

`query`로 로그인 실패 로그를 선택하고, `background_filter`로 같은 서비스·기간의 전체 로그인 로그를 비교 기준으로 정한다. 이렇게 찾은 계정을 중심으로 접속 IP와 시간대, 성공·실패 기록을 살펴보며 조사할 범위를 좁힐 수 있다.

프로세스 실행 로그에서도 같은 방식으로 특정 호스트에서 전체 호스트보다 두드러지는 `process.name`을 찾을 수 있다. **전체에서 흔한 값에 가려진, 조사 대상의 특징을 드러내는 것**이 이 집계의 활용 포인트다.

## 6. 마무리

1. 코르티스 글의 최빈 태그를 찾는다면 어느 집계를 쓸까? → `terms`.
2. 코르티스 글에서 전체보다 두드러지는 태그를 찾는다면? → `significant_terms`.
3. 같은 코르티스 글만 `background_filter`로 지정하면? → 선택 집합과 배경이 같아져 JLH에서 양의 점수를 얻는 태그가 없다.
4. 영크크가 모든 그룹에서 비슷한 비율로 쓰이게 된다면? → 코르티스의 특징으로서의 점수는 낮아진다.
5. SIEM의 로그인 실패 로그에 적용한다면 무엇을 찾을 수 있을까? → 전체 로그인 로그와 비교해 실패 로그에서 두드러지는 계정
